# `ros_support`

`ros_support` — универсальный плагин пакета `clover2_http`. Он предоставляет REST API, с помощью которого можно получить список нод и топиков, просмотреть издателей, подписчиков и сервисы каждой ноды, а также узнать текущее состояние lifecycle-ноды и выполнить переход между состояниями. Для передачи сообщений топиков используется WebSocket-интерфейс. 

Для сериализации сообщений используется механизм typesupport (`rosidl_typesupport_introspection_cpp`). Благодаря этому плагин не зависит от конкретных типов ROS 2 сообщений: он может обрабатывать сообщения разных типов без предварительного описания их структуры в коде плагина.

## Маршруты

Плагин предоставляет следующие HTTP- и WebSocket-маршруты:

| Метод | Путь | Описание |
| --- | --- | --- |
| GET | `/api/topics` | Получить список всех топиков графа с указанием имени и типа каждого топика `{name, type}` |
| GET | `/api/nodes` | Получить список имен всех нод |
| GET | `/api/node/info/-/{node...}` | Получить информацию о ноде: имя, пространство имен, наличие поддержки lifecycle и текущее состояние |
| GET | `/api/node/publishers/-/{node...}` | Получить список издателей ноды с указанием топиков и QoS-профилей |
| GET | `/api/node/subscribes/-/{node...}` | Получить список подписчиков ноды с указанием топиков и QoS-профилей |
| GET | `/api/node/servers/-/{node...}` | Получить список сервисов, предоставляемых нодой |
| GET | `/api/node/clients/-/{node...}` | Получить список клиентов сервисов ноды |
| GET | `/api/node/lifecycle/available_transitions/-/{node...}` | Получить список переходов, доступных из текущего состояния lifecycle-ноды |
| POST | `/api/node/lifecycle/transition/-/{node...}` | Выполнить переход lifecycle-ноды в другое состояние |
| WS | `/ws/topic/json/-/{topic...}` | Подключиться к потоку сообщений топика в формате JSON |

Capabilities плагина: `nodes`, `topics`, `services`.

## Параметры

| Параметр | По умолчанию | Описание |
| --- | --- | --- |
| `ros_support.topics_rate_limit_bps` | `100000.0` | Общее ограничение скорости передачи данных всех топиков, байт/с |

## Управление lifecycle-нодами

ROS 2 поддерживает механизм управления жизненным циклом нод. Такие ноды могут находиться в разных состояниях, а их переходы между состояниями выполняются через специальные сервисы. Плагин `ros_support` позволяет получать список доступных переходов и выполнять их через REST API.

### Получение доступных переходов

Отправьте GET-запрос: `GET /api/node/lifecycle/available_transitions/-/{node...}`.

В ответ сервер возвращает список переходов, доступных из текущего состояния ноды. Каждый переход содержит:
* `transition` — информацию о переходе;
* `start_state` — исходное состояние ноды;
* `goal_state` — состояние, в которое перейдет нода после выполнения перехода.

Пример ответа:

```json
{
  "available_transitions": [
    {
      "transition": { "label": "configure" },
      "start_state": { "label": "unconfigured" },
      "goal_state": { "label": "inactive" }
    }
  ]
}
```

### Выполнение перехода

Для выполнения перехода отправьте POST-запрос:`POST /api/node/lifecycle/transition/-/{node...}`.

В теле запроса передайте JSON-объект с полем `label`, содержащим название перехода.
Например, чтобы выполнить переход `configure` для ноды `map_server`, используйте команду:

```bash
curl -X POST http://localhost:8080/api/node/lifecycle/transition/-/map_server \
    -H 'Content-Type: application/json' \
    -d '{"label": "configure"}'
```

Возможные HTTP-коды ответа:

- `200` — переход выполнен успешно;
- `409` — нода отклонила переход (например, если запрошен переход `activate`, когда нода находится в состоянии `unconfigured`);
- `502` — не удалось вызвать сервис ноды (например, если нода недоступна).

## Стриминг сообщений

Каждое ROS 2 сообщение передается отдельным текстовым WebSocket-фреймом. При сериализации:
* имена полей JSON соответствуют именам полей в определении ROS 2 сообщения (`.msg`);
* вложенные сообщения преобразуются во вложенные JSON-объекты;
* массивы преобразуются в JSON-массивы.
  
Например, сообщение топика `/rosout типа rcl_interfaces/msg/Log` может выглядеть так:

```json
{"file":"./src/topics/talker.cpp","function":"operator()","level":20,"line":47,"msg":"Publishing: 'Hello, 0'","name":"talker","stamp":{"nanosec":521751302,"sec":1756200000}}
```

Если сервер не может установить WebSocket-соединение, он возвращает HTTP-ответ с кодом ошибки и JSON-объектом: `{"error": "<message>"}`.

Если HTTP-код ответа отличается от `200`, следует проверить поле `error`.

После успешного установления WebSocket-соединения ошибки и причины закрытия передаются через коды закрытия WebSocket:

- `1008` — указанный топик отсутствует в графе ROS 2 на момент подключения;
- `1011` — внутренняя ошибка сервера;
- `1001` — сервер закрыл соединение из-за отсутствия входящих фреймов в течение 60 секунд.

```{important}
Чтобы соединение оставалось активным, клиент должен периодически отправлять серверу текстовые WebSocket-фреймы.
Содержимое этих фреймов сервер игнорирует, но их получение сбрасывает таймер бездействия.
Если клиент не отправляет входящие фреймы в течение 60 секунд, сервер автоматически закрывает WebSocket-соединение. 
```

## Ограничения потока

Для получения сообщений плагин создает универсальные (generic) подписки с QoS-профилем `best_effort` и глубиной очереди `10`. Из-за этого при высокой нагрузке часть сообщений может пропускаться. 

Скорость передачи данных ограничивается параметром `ros_support.topics_rate_limit_bps`.  Ограничение применяется ко всему потоку передаваемых сообщений независимо от топика.
